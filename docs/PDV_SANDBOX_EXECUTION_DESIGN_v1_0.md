# PDV 볼트 코드 실행 샌드박스 설계 v1.0
## "데이터가 아니라 코드를 보낸다" — Compute-to-Data 실행 아키텍처

> 전제 문서: [`PDV_INSURANCE_SYSTEM_DESIGN_v2_0.md`](./PDV_INSURANCE_SYSTEM_DESIGN_v2_0.md) §2(동의)·§5(아키텍처)의 "PDV 접근 게이트웨이"를 이 문서가 구체화한다. 이 문서 이후로는 게이트웨이가 "집계치를 꺼내오는" 방식이 아니라, **보험사 코드를 혼디 신뢰 경계 안으로 불러들여, 원본 PDV는 경계를 넘지 않고, 서명된 결과만 내보내는** 방식으로 대체된다.

---

## 1. 위협 모델 — 무엇으로부터 무엇을 지키는가

이 설계가 실제로 안전하려면 세 종류의 서로 다른 신뢰 문제를 각각 다른 메커니즘으로 풀어야 한다. 하나라도 빠지면 전체가 무너진다.

| # | 질문 | 이 문서가 다루는 메커니즘 |
|---|---|---|
| ① 실행 무결성 | "이번 결과가 정말 공개된 그 코드가, 변조 없이 실행된 결과인가?" | 코드 해시 고정 + 격리 실행 + 서버 서명 (§4, §6) |
| ② 데이터 비유출 | "보험사 코드가 원본 PDV를 몰래 빼돌리지 않는가?" | 네트워크 격리 + 캡슐화된 조회 API(§5) |
| ③ 결과를 통한 역추정 | "결과값을 여러 번 뽑아서 원본을 재구성할 수 없는가?" | 결과 조악화 + 재실행 빈도 제한(§7) |

이 셋을 다 갖춰야 "코드를 보낸다"가 실제로 "데이터를 안 보낸다"와 같은 뜻이 된다. 하나라도 빠지면 결국 데이터를 보내는 것과 실질적으로 다르지 않다.

## 2. 코드 생애주기 — 제출부터 실행까지

```
[보험사]
   │ ① 오픈소스 리포에 스코어링 코드 게시 (예: github.com/{insurer}/pdv-scoring-auto)
   ▼
[코드 등록]  POST /sandbox/register-code
   │ { repo_url, commit_sha, entry_point, declared_input_schema, declared_output_schema }
   ▼
[정적 심사]  (자동 + 사람)
   │  - 금지 API 호출 여부(네트워크, 파일시스템, eval 등) 정적 분석
   │  - 선언된 output_schema가 §7의 "조악화 규칙"을 만족하는지 검사
   │  - 코드 해시 = SHA-256(commit_sha 시점의 entry_point 파일 트리)
   ▼
[인증 등록부(Registry)]  PocketBase `sandbox_certified_code` 컬렉션
   │  { code_hash, repo_url, commit_sha, cert_level: "auto"|"reviewed", certified_at }
   ▼
[동의 시점에 code_hash를 스코프 토큰에 고정]  (PDV_INSURANCE_SYSTEM_DESIGN_v2_0.md §2.2 확장)
   │  scope_token.pinned_code_hash = "abcd1234..."
   ▼
[실행 요청]  POST /sandbox/execute { scope_token, code_hash }
   │  → code_hash가 scope_token.pinned_code_hash와 다르면 즉시 거부(§4)
   ▼
[격리 실행] → [결과 서명] → [OpenHash 앵커링] → [보험사에게 결과 반환]
```

**핵심 규칙: 코드가 바뀌면(commit_sha가 바뀌면) code_hash도 바뀌고, 사용자는 재동의해야 한다.** 이걸 강제하지 않으면 "오픈소스니까 검증 가능하다"는 전제가 실제 실행 시점엔 무의미해진다 — 사용자가 승인한 건 v1.2였는데 실행되는 건 v1.7일 수 있기 때문이다.

## 3. 인증 레벨 — 모든 코드를 같은 기준으로 취급하지 않는다

오픈소스로 공개돼 있다고 해서 자동으로 "실행해도 안전하다"는 뜻은 아니다(사이드채널, 리소스 남용, 교묘한 출력 인코딩을 통한 정보 유출 등은 코드를 눈으로 읽는 것만으로 다 못 잡는다). 그래서 2단계 인증 체계를 둔다.

| 인증 레벨 | 조건 | 실행 시 제약 |
|---|---|---|
| **`auto`** (정적 심사만 통과) | 자동 분석기가 금지 패턴 없음을 확인 | 리소스 상한 더 낮게, 실행 로그 표본을 사람이 주기적으로 재검토, 사용자당 실행 빈도 더 낮게 |
| **`reviewed`** (사람 검토 완료) | 최소 2인의 독립 검토자(사내 보안팀 + 외부 감사 중 택1 이상 권장)가 코드를 직접 읽고 승인 | 표준 제약(§7) 적용 |

신규 코드는 항상 `auto`로 시작하고, 검토를 거쳐야 `reviewed`로 승격한다. 이 등록부 자체도 공개한다 — 어떤 코드가 어떤 레벨인지 누구나 조회 가능해야, "오픈소스 투명성"이 등록부 차원에서도 성립한다.

## 4. 격리 실행 환경

### 4.1 기술 선택 — Cloudflare Workers for Platforms

혼디 인프라가 이미 Cloudflare Workers(`hondi-proxy.tensor-city.workers.dev`) 기반이므로, 신규 인프라를 새로 들이지 않고 **Workers for Platforms(동적 디스패치 네임스페이스)** 를 쓴다.

- 보험사 코드를 별도 **디스패치 네임스페이스**에 업로드해 격리한다(혼디 메인 워커와 완전히 분리된 실행 컨텍스트).
- **바인딩을 아무것도 주지 않는 것이 기본값**이다 — Cloudflare Workers는 `fetch()` 같은 외부 네트워크 호출도 명시적으로 바인딩하지 않으면 실행 컨텍스트에 나가는 길 자체가 없다. 즉 보험사 코드에 **원본 PDV로 가는 길도, 바깥 인터넷으로 나가는 길도 기본적으로 존재하지 않는다.**
- 유일하게 주어지는 바인딩은 §5의 **PDV 조회 캡슐 API 하나뿐**이다.
- CPU 시간(수십 ms 단위)·메모리·실행 시간이 플랫폼 차원에서 이미 제한되어 있어, 무한루프·리소스 고갈형 공격이 구조적으로 어렵다.

```
디스패치 요청 예시
env.SANDBOX_DISPATCHER.get(code_hash).fetch(
  new Request("https://sandbox.internal/run", {
    method: "POST",
    body: JSON.stringify({ pdv_capsule_token, policy_context }),
  })
)
```

### 4.2 실행 전 체크리스트 (매 실행마다)

1. `code_hash == scope_token.pinned_code_hash` 확인
2. `scope_token` 서명·만료·철회 여부 확인 (v2.0 §2.2)
3. 등록부에서 해당 `code_hash`의 인증 레벨 확인 → 레벨별 리소스 상한 적용
4. 같은 `(user, code_hash, scope_id)` 조합의 최근 실행 빈도 확인 (§7.2)
5. 위 넷 중 하나라도 실패 시 실행 자체를 거부하고 감사 로그에 사유 기록

## 5. PDV 조회 캡슐 API — "직접 접근" 대신 "질문에만 답하는" 인터페이스

보험사 코드에게 PDV 원장을 통째로 넘기지 않는다. 대신 **동의 스코프에 이미 선언된 질문에만 답하는 좁은 객체**를 주입한다.

```js
// 보험사 코드 안에서 사용 가능한 것은 이게 전부다
async function score(pdv) {
  // pdv는 원본 레코드 열람이 아니라, 스코프에 선언된 항목만 응답하는 캡슐
  const nightDrivingRatio = await pdv.query("k-traffic.night_ratio_monthly");
  const accidentFreeMonths = await pdv.query("k-traffic.accident_free_months");
  // pdv.query("k-health.diagnosis")  ← 스코프에 없으면 여기서 즉시 예외, 호출 자체가 차단됨

  let score = BASE - nightDrivingRatio * 0.4 + Math.min(accidentFreeMonths, 36) * 0.2;
  return { grade: bucketize(score) };   // §7 — 연속값이 아니라 등급으로만 반환
}
```

- `pdv.query()`가 받아들이는 키 목록은 **스코프 토큰에 사전 선언된 화이트리스트**뿐이다. 목록에 없는 키를 요청하면 그 즉시 실행이 중단되고 위반으로 기록된다(코드가 스코프를 넘어서려 한 시도 자체가 감사 대상).
- `pdv.query()`가 실제로 반환하는 값도 **이미 집계·정제된 값**이다(v2.0 §2.2의 "집계 우선" 원칙 재사용) — 원본 이벤트 로그가 이 함수 안으로 들어오는 일 자체가 없다.
- 이 캡슐 객체 자체는 PDV 볼트가 실행 직전에 즉석으로 만들어 디스패치 요청에 실어 보내고, 실행이 끝나면 폐기된다(영속 저장 안 함).

## 6. 결과 서명 및 OpenHash 앵커링

실행이 끝나면, 결과를 보험사에 그냥 돌려주지 않고 **다음 네 가지를 묶어 혼디 서버 키로 서명한 뒤 OpenHash에 앵커링**한다.

```json
{
  "code_hash": "sha256:abcd1234...",
  "input_commitment": "sha256:ef567...",   // 실제 입력값이 아니라 입력값의 해시(커밋먼트)
  "scope_token_id": "ins-auto-underwrite-v1:user_guid:2026-07",
  "output": { "grade": "B" },
  "executed_at": "2026-07-26T07:10:00Z",
  "signature": "hondi-server-ed25519:..."
}
```

- **`input_commitment`**: 입력값 원문이 아니라 해시만 남긴다. 나중에 분쟁이 생기면(§8) 사용자가 자기 PDV로 같은 계산을 재현해 이 해시와 일치하는지 검증할 수 있지만, 이 기록 자체만으로는 원본을 알 수 없다.
- **혼디 서버 서명**: 보험사는 "이 결과가 혼디 인프라 안에서, 이 code_hash로, 이 시각에 실제로 산출됐다"는 것을 이 서명으로 확인한다 — 보험사가 스스로 신뢰할 근거가 된다.
- **OpenHash 앵커링**: 나중에 감독기관·분쟁 상황에서 "이 보험료가 왜 이렇게 나왔는지" 재현 가능한 불변 기록으로 남는다(v2.0 §2.2가 요구했던 감사 가능성의 구현체).

## 7. 결과 조악화 및 재실행 제한 — 결과를 통한 역추정 방지

### 7.1 출력 스키마 강제

등록 심사(§2) 단계에서 `declared_output_schema`가 다음 중 하나에 속하지 않으면 등록 자체를 거부한다:

- **등급형**: 사전 정의된 유한 집합(예: `{A, B, C, D}`) 중 하나
- **버킷형 수치**: 연속값이 아니라 폭이 정해진 구간(예: 5% 단위 구간)으로 반올림된 값
- 자유 형식 실수·정수·문자열은 허용하지 않는다 — 정밀한 연속값은 그 자체로 시계열 추적 시 정보 유출 통로가 된다(v1.0 초안 논의에서 지적된 문제)

### 7.2 재실행 빈도 제한

같은 `(user, code_hash, scope_id)` 조합은 **스코프에 선언된 재산정 주기(기본: 월 1회, v2.0 §4.1과 동일)** 를 넘어 재실행할 수 없다. 보험사가 여러 다른 입력 가정으로 결과를 여러 번 뽑아보며 원본을 추론하는 차분 공격(differencing attack)을 구조적으로 어렵게 만든다.

- 예외적으로 더 잦은 재산정이 필요한 상품(예: 실시간 이벤트 보험)은 개별 심사를 거쳐 별도 한도를 부여하되, 반드시 §7.1의 등급형 출력과 결합해야 한다(빈도가 높아질수록 출력은 더 거칠어야 한다 — 트레이드오프를 명시적으로 강제).
- 모든 실행 시도(성공·거부 모두)는 감사 로그에 남고, 동일 스코프에 대해 짧은 시간 내 다수의 실행이 몰리면 자동으로 플래그되어 사람이 검토한다.

## 8. 사용자 재현·검증 경로

사용자는 언제든 다음을 할 수 있어야 한다(이게 없으면 "투명성"이 이론에 그친다):

1. **자기 실행 이력 조회**: `GET /sandbox/my-executions` — 언제, 어떤 code_hash로, 어떤 scope로 실행됐는지 전체 이력.
2. **재실행(셀프 검증)**: 같은 `code_hash`(등록부에서 원본 리포·커밋 그대로 조회 가능)를 자기 PDV에 대해 직접 돌려보고, 그 결과가 OpenHash에 앵커링된 결과와 같은지 확인. 이 경로는 §7.2의 빈도 제한과 별도로, 본인 검증 목적에 한해 예외를 둔다.
3. **이의 제기**: 재현 결과가 다르면(코드가 몰래 바뀌었거나, 캡슐 API가 오작동했다는 뜻) 즉시 이의 제기 창구로 연결 — v2.0 §5의 "사람 담당자 검토" 경로와 동일하게 처리.

## 9. 잔여 위험 (이 설계로도 완전히 안 풀리는 것들)

- **사이드채널**: 아무리 격리해도, 실행 시간·메모리 사용 패턴 같은 부수 정보가 (극단적인 경우) 입력에 대한 힌트를 흘릴 수 있다 — Workers for Platforms는 이런 정밀 사이드채널 공격에 대한 완벽한 방어를 표방하지 않는다. 초기 단계에서는 수용 가능한 잔여 위험으로 간주하되, 고액·고민감 상품(생명보험 등)으로 확장할 때는 재검토가 필요하다.
- **정적 심사의 한계**: `auto` 레벨은 사람이 안 읽었다는 뜻이다 — 정적 분석기가 못 잡는 교묘한 로직(예: 특정 조건에서만 발동하는 우회 경로)은 통과할 수 있다. 따라서 §3처럼 `auto` 코드는 실행 빈도·리소스를 더 강하게 제한하고, 실제 서비스에 널리 쓰이려면 `reviewed`로 승격을 강제하는 정책(예: 월 실행 1만 건 이상이면 반드시 reviewed)을 두는 걸 권한다.
- **보험사 쪽 데이터 조합 공격**: 이 설계는 "한 번의 실행에서 원본이 새지 않는다"에 집중한다. 하지만 보험사가 여러 다른 상품·여러 다른 code_hash로 **같은 사용자에 대해 여러 조각의 등급 정보를 모아 재조합**하면, 개별로는 거칠어도 합쳐서 프로파일을 재구성할 수 있다(모자이크 효과). 이건 개별 실행 설계가 아니라 **사용자 단위로 전체 노출 이력을 총량 관리하는 상위 정책**이 별도로 필요하다 — v2.0/이 문서의 범위를 넘는 후속 과제로 남긴다.

| 항목 | v2.0 (게이트웨이가 집계치를 꺼내온다) | v2.1 (이 문서: 코드가 안으로 들어온다) |
|---|---|---|
| 원본 PDV 이동 | 게이트웨이가 원본에서 집계치를 계산해 밖(리스크 피처 스토어)으로 내보냄 | 원본이 혼디 신뢰 경계를 아예 벗어나지 않음 — 계산 자체가 경계 안에서 일어남 |
| 로직 검증 가능성 | 리스크 피처 스토어의 집계 로직은 혼디 쪽 코드(비공개 가능) | 보험사 스코어링 로직 자체가 오픈소스로 공개, 코드해시로 고정 |
| 실행 무결성 증명 | 없음(암묵적으로 혼디를 신뢰) | 코드해시+입력커밋+서명+OpenHash 앵커링으로 명시적 증명 |
| 결과 형태 | 리스크 팩터(수치) | 강제된 등급/버킷형 출력만 허용 |
