# PDV 기반 보험 시스템 설계 v2.0
## K-Insurance — PDV 연동 보험료 산정·인수·청구 시스템

> 관계 문서: [`DESIGN.md`](./DESIGN.md)(v1.0, 2026년 초안) · [`API.md`](./API.md) · `gopang/docs/business-plan/*`
> **v1.0과의 관계**: v1.0은 "종래의 보험회사를 AI로 완전 대체"를 지향하는 마케팅·제품 비전 문서였고, 실제 구현(`kinsurance-claim.js`)은 자동 심사·자동 지급 없이 담당자 검토만 하는 상태였다 — 문서와 코드가 어긋나 있었다. v2.0은 그 간극을 인정하고, **실제로 만들 수 있고 법적으로 버틸 수 있는 시스템**을 처음부터 다시 설계한다. v1.0의 "AI가 0.3초 안에 심사·지급" 같은 표현은 이 문서에서 전부 폐기한다.

## 0. 설계 원칙

1. **PDV는 언더라이팅의 입력이지, 보험업 인허가의 대체물이 아니다.** 아무리 데이터가 좋아도 위험을 인수(underwrite)하고 보험금을 지급하는 행위는 한국 보험업법상 인허가 사업이다. 이 설계는 "누가 실제로 위험을 인수하는가"라는 질문에 처음부터 답하고 시작한다 (§1).
2. **가족 건강 이력을 개인 보험료에 직접 연결하지 않는다.** 사용자가 제안한 대로 PDV가 가족 건강·질병 이력까지 포함한다는 전제는 유지하되, 이를 개인 단위 보험료 산정에 직접 반영하는 것은 유전정보 차별(genetic discrimination)과 사실상 동일한 효과를 낼 수 있어 별도의 엄격한 게이트를 둔다 (§4.3).
3. **동의는 목적 단위로 세분화하고, 철회 가능하며, 감사 가능해야 한다.** "PDV 전체를 보험사에 넘긴다" 같은 포괄 동의는 설계하지 않는다 (§2).
4. **실시간·자동 심사는 저위험·저액 청구부터, 확률적으로 확장한다.** "모든 청구를 0.3초에 처리"가 아니라, 사기 위험이 낮고 금액이 작은 청구군부터 자동화하고 나머지는 사람이 본다 — 지금 실제 코드가 하고 있는 "담당자 검토"를 폄하하지 않고 그 위에 단계적으로 쌓는다.
5. **사물(자동차 등)과 사람은 다른 트랙으로 설계한다.** 사물 보험(UBI형 자동차보험)은 이미 산업 표준(텔레매틱스 기반)이 있어 법·기술 리스크가 낮다. 건강·생명 보험은 훨씬 민감하고 규제가 두껍다. 두 트랙을 같은 일정으로 밀어붙이면 안 된다 (§6 로드맵).

## 1. 법적 골격 — "누가 위험을 인수하는가"

PDV 데이터가 아무리 정교해도, 혼디(AI City Inc.)가 스스로 보험업을 영위하려면 보험업법상 보험회사 또는 통신판매업 특례 등 인허가가 필요하다. 세 가지 현실적 트랙이 있고, 각각 PDV 시스템 설계에 미치는 영향이 다르다.

| 트랙 | 구조 | PDV의 역할 | 현재 단계 적합성 |
|---|---|---|---|
| **A. MGA/보험대리점 모델** | 혼디는 인수 주체가 아니라, 기존 인가 보험사·재보험사와 제휴해 "PDV 기반 언더라이팅 엔진 + 청구 전처리"를 제공하는 대리점(MGA, Managing General Agent) 역할 | 리스크 스코어링·보험료 산출 로직을 제공하고, 실제 계약·지급은 제휴 보험사 명의 | ★★★ 가장 현실적. 자본 요건 없이 시작 가능 |
| **B. 공제(共濟)/상호부조 모델** | 회원제 상호부조 조합 형태로, "보험"이라는 명칭을 피하고 소액·자율 갹출 기반 상호부조로 설계(기존 새마을금고 공제, 각종 협동조합 공제와 유사 구조) | 회원 간 리스크 풀링의 배분 기준으로 PDV 사용 | ★★☆ 제주 시범 규모에 적합하나 감독당국 해석에 따라 여전히 보험업법 적용 소지 있음 — 법률 자문 필수 |
| **C. 자체 보험업 인가** | 소액단기보험업(2022년 도입된 미니보험업, 자본금 20억원) 등 완화된 인가 트랙을 직접 취득 | 완전한 자체 인수·지급 | ★☆☆ 장기 목표. 초기엔 비현실적 |

**이번 설계는 A(MGA 모델)를 기본 가정으로 삼는다.** 즉 이 문서의 "보험료 산정 엔진"은 **제휴 보험사에 제출할 언더라이팅 자료를 만드는 시스템**으로 설계하고, "자동 지급"은 제휴사의 승인 하에 이루어지는 대위 지급으로 표현한다. 이렇게 하면 지금 이미 존재하는 GDC 결제·PDV 기록·OpenHash 앵커링 인프라를 거의 그대로 재사용하면서, 인허가 문제를 안고 가지 않는다.

> ⚠️ 이 절은 법률 자문이 아니다. 실제 트랙 선택 전 보험업법·전자금융거래법 전문 변호사 검토가 반드시 필요하다.

## 2. 동의·데이터 거버넌스 아키텍처

### 2.1 왜 "전체 동의"가 안 되는가

개인정보보호법상 건강정보는 민감정보로, 일반 개인정보보다 훨씬 엄격한 별도·명시적 동의가 필요하다. PDV가 6하원칙(누가·언제·어디서·무엇을·어떻게·왜)으로 사용자의 일상·업무·건강 이력을 포괄적으로 기록한다는 전제 자체가, "보험료 산정을 위해 PDV 전체를 넘긴다"는 식의 포괄 동의를 더 위험하게 만든다. 목적이 명확하지 않은 광범위한 동의는 최소수집 원칙(개인정보보호법 §3)에 저촉될 소지가 크다.

### 2.2 스코프 기반 동의 모델

PDV 접근을 **보험 상품별 · 데이터 카테고리별 · 기간별로 쪼갠 스코프 토큰**으로 설계한다.

```
동의 스코프 예시 (자동차 보험 가입 시)
{
  "scope_id": "ins-auto-underwrite-v1",
  "purpose": "자동차 보험 보험료 산정",
  "data_categories": ["k-traffic.driving_events"],   // 건강 데이터 접근 안 함
  "granularity": "aggregated_monthly",                // 원본 이벤트가 아니라 월별 집계치만
  "lookback_window": "12_months",
  "issuer": "user_wallet_signature",                  // 사용자 지갑 서명 필수
  "revocable": true,
  "expires_at": "2027-07-26T00:00:00Z",
  "audit_anchor": "openhash://..."                    // 동의 자체도 OpenHash에 앵커링
}
```

- **카테고리 분리**: "자동차 보험"은 K-Traffic 운행 데이터만 요청할 수 있고, 건강 데이터는 요청 자체가 불가능하도록 스코프 정의 단계에서 차단한다(상품별 화이트리스트).
- **집계 우선(Aggregation-first)**: 가능하면 원본 이벤트(예: 특정 시각·장소의 GPS 로그)가 아니라 이미 집계된 지표(예: "월 평균 야간 운행 비율")만 보험 엔진에 노출한다 — 보험 엔진이 원본 PDV를 직접 열람하지 못하게 하는 것이 사고 발생 시 프라이버시 침해 반경을 줄이는 핵심 설계다.
- **철회**: 사용자가 동의를 철회하면, 이후 갱신 주기부터 해당 팩터는 "미제공"으로 처리되어 중립값(할인·할증 없음)으로 대체된다 — 철회했다고 보험 가입 자체가 불가능해지진 않는다(단, 그만큼 보험료는 "정보 부족 시 표준 요율"이 적용되어 평균적으로 더 비쌀 수 있음을 사전 고지).
- **감사 가능성**: "이 보험료는 어떤 PDV 데이터를 근거로 산출됐는가"를 사용자가 언제든 조회할 수 있어야 한다 — 동의 자체와 실제 산출에 쓰인 팩터 스냅샷을 OpenHash에 앵커링해, 나중에 분쟁이 생기면(예: "내 보험료가 왜 올랐지?") 그 시점의 근거를 재현할 수 있게 한다.

### 2.3 가족 구성원 데이터

PDV가 가족의 건강 이력을 포함한다는 전제 자체는 그대로 두되, **가족 구성원 개인의 명시적 동의 없이 그 사람의 건강 데이터가 다른 가족 구성원(본인)의 보험료 산정에 쓰이는 것은 원칙적으로 금지**한다. 이는 §4.3에서 더 다룬다.

## 3. 리스크 분류 트랙 — 상품군별 설계

사용자가 언급한 "사람뿐 아니라 사물·개념도 사용자"라는 전제를 살려, 두 개의 독립된 언더라이팅 트랙으로 나눈다.

### 3.1 트랙 1 — 사물 보험(자동차 등): UBI(Usage-Based Insurance)

가장 성숙하고 법적 리스크가 낮은 트랙. 이미 K-Traffic이 실제로 운행 이벤트를 기록하고 있으므로(§ traffic 저장소 확인됨), 이를 그대로 재사용한다.

**리스크 팩터(예시, 실측 후 계수 조정 필요)**

| 팩터 | 데이터 출처 | 산정 방식 |
|---|---|---|
| 주행 거리·빈도 | K-Traffic 이벤트 로그 (월 집계) | 노출도(exposure) 기본 단위 |
| 야간·새벽 운행 비율 | K-Traffic (23시~05시 구간 비율) | 사고율과 상관관계가 문헌상 확인된 팩터 — 임계치 초과 시 할증 |
| 급가속·급제동 빈도 | K-Traffic 텔레매틱스(가속도 이벤트) — **현재 미수집, 개발 필요** | 방어운전 지표 |
| 무사고 경과 기간 | K-Traffic 사고 이벤트 이력 부재 기간 | 할인 — 단, "무사고"의 정의를 사고 미보고와 혼동하지 않도록 청구 이력과 별도 검증 |
| 차량 사용 목적 | 사용자 신고(영업용/자가용) | 기본 요율 구간 결정 |

**설계 포인트**: UBI는 데이터가 쌓일수록 개인 경험치(credibility)가 늘어나므로, 신규 가입자는 인구통계학적 기본 요율(연령·차종·지역)에서 시작해, 운행 데이터가 3~6개월 쌓이면 점진적으로 개인 데이터 비중을 높이는 **크레더빌리티 가중 모델**을 쓴다(§4.2).

### 3.2 트랙 2 — 사람 대상 건강·생명 보험

가장 민감한 트랙. 초기엔 **"이벤트 기반 소액 정액보험"만 취급**하고, 정통 실손·생명보험처럼 개인별 정밀 언더라이팅이 필요한 상품은 뒤로 미룬다.

| 상품 형태 | 예시 | PDV 활용 범위 | 인수 난이도 |
|---|---|---|---|
| 이벤트 트리거 정액보험 | 응급실 방문 시 정액 ₮N 지급 | K-119/K-Health의 "이벤트 발생 여부"만 확인(진단명·병력은 열람 안 함) | 낮음 — 지금 코드 구조와 가장 가까움 |
| 정기검진 연동 소액 할인 | 연 1회 정기검진 완료 시 다음 갱신 보험료 할인 | "완료 여부"(boolean)만 확인, 검진 결과는 열람 안 함 | 낮음 |
| 실손 의료보험 | 병원비 실비 보상 | 진단명·처치 내역까지 필요 — 훨씬 민감 | 높음 — 제휴 보험사(트랙 A) 없이는 사실상 불가 |
| 생명보험(사망·장해) | 정기·종신 | 계약 시점 건강 상태 전반 심사 필요, 가족력 등 유전 관련 요인 개입 소지 | 매우 높음 — §4.3 게이트 적용, 장기 과제 |

**설계 포인트**: "정액 이벤트 보험"은 진단명이나 구체적 병력을 몰라도 "이벤트가 실제로 발생했는가"만 K-Health/K-119 쪽에서 **불리언 어테스테이션(boolean attestation)**으로 받아오면 되므로, 프라이버시 노출을 최소화하면서도 실제로 자동화할 수 있는 첫 상품군이다.

## 4. 보험료 산정 방법론

### 4.1 기본 공식

```
월 보험료 = 기준요율(상품·구간) × Π(리스크팩터_i)^가중치_i × 크레더빌리티조정 + 고정관리비
```

- **기준요율**: 상품별로 감독당국 신고 대상이 될 수 있는 값(트랙 A/제휴사 요율표 기준). PDV 팩터는 이 기준요율에 곱해지는 **상대도(relativity)**로만 작동 — "PDV가 보험료를 결정한다"가 아니라 "PDV가 기준요율을 조정한다"는 구조로, 규제 설명이 훨씬 쉽다.
- **팩터 상한·하한**: 어떤 팩터도 단독으로 ±30%를 초과해 조정하지 않도록 캡을 둔다(초기값, 실측 데이터로 조정) — 팩터 하나의 노이즈가 보험료를 널뛰게 하는 것을 막고, "왜 이번 달 보험료가 2배가 됐냐"는 분쟁을 구조적으로 방지한다.
- **갱신 주기**: 실시간이 아니라 **월 단위 재산정**을 기본으로 한다. 실시간 재산정은 사용자에게 예측 불가능한 비용 부담을 주고, 규제상으로도 "보험료 산정 근거의 안정성" 요건과 충돌할 수 있다.

### 4.2 크레더빌리티(신뢰도) 가중 — 데이터가 적을 때의 문제

보험수리학의 표준 기법인 **뷜만(Bühlmann) 크레더빌리티**를 단순화해 적용한다:

```
개인 최종 리스크 스코어 = Z × (개인 PDV 관측치) + (1 − Z) × (동질집단 평균)
Z = n / (n + k)   // n: 관측 기간(개월) 또는 이벤트 수, k: 안정화 상수(상품별 튜닝)
```

가입 초기(n이 작을 때)엔 Z가 작아 동질집단(연령·지역·차종 등 인구통계 기반) 평균에 가깝게 산정되고, PDV 관측치가 쌓일수록(n 증가) 개인화 비중이 늘어난다. 이렇게 하면 "가입 첫 달인데 데이터가 없다고 보험 가입 자체를 거부"하는 문제를 피하면서도, 소수의 초기 관측치로 극단적인 할인·할증을 주는 과적합을 막는다.

### 4.3 가족력·유전 관련 데이터 게이트 (중요)

사용자가 제안한 "가족의 건강·질병 이력이 보험료 산정에 이상적"이라는 부분은 **가장 신중하게 다뤄야 할 지점**이다.

- **원칙적으로 개인 보험료 산정에 가족 구성원 개별 병력을 직접 입력값으로 쓰지 않는다.** 부모의 특정 질환 이력을 자녀의 생명·건강보험 요율에 직결시키면, 이는 사실상 유전정보 차별과 동일한 효과를 낸다 — 미국은 GINA(유전정보차별금지법)로 이를 명시적으로 금지하고, 한국은 아직 이에 준하는 명문 규정이 촘촘하진 않지만 생명윤리법·개인정보보호법의 민감정보 규율 취지상 매우 위험한 영역이다.
- **대신 허용하는 방식**: (a) 가족력을 개인이 아닌 **익명화·집계된 통계**로만 반영(예: "직계가족 중 조기 심혈관질환 이력 있음/없음"의 이진 플래그를 본인이 자발적으로 신고하는 기존 생명보험 청약서 방식과 동일 수준까지만 — PDV가 자동으로 끌어오지 않고, 사용자가 원하면 스스로 공개하는 opt-in 방식), (b) 가족력 반영 여부와 무관하게 표준 요율 상품을 항상 병행 제공해 "정보를 안 주면 아예 가입이 안 된다"는 상황을 막는다.
- **이 부분은 초기 로드맵(§6)에서 아예 제외**하고, 별도의 생명윤리·법률 자문을 거친 뒤 훨씬 나중 단계에서 재검토한다.

### 4.4 준비금·재보험

혼디가 트랙 A(MGA)로 간다면 준비금 적립·재보험 계약은 제휴 보험사의 몫이지만, 시스템 설계상 다음은 반드시 필요하다:
- **IBNR(발생했으나 미보고된 손해) 추정**: 청구 데이터가 쌓이면 지연 신고 패턴을 분석해 준비금 추정치를 산출하는 배치 작업.
- **대재해 익스포저 모니터링**: 특정 지역·기간에 이벤트 보험(탑승·배달 등) 청구가 급증하면(예: 폭설로 배달 사고 급증) 이를 조기 탐지해 제휴 보험사·재보험사에 통지하는 알림 체계.

## 5. 시스템 아키텍처

기존에 이미 실재하는 컴포넌트(지갑 서명, `/biz/ins-claim`, PocketBase L1, OpenHash, GDC)를 최대한 재사용하고, 신규 컴포넌트만 추가한다.

```
[PDV 원장] ──(스코프 동의 토큰)──▶ [PDV 접근 게이트웨이] ──(집계치만)──▶ [리스크 피처 스토어]
                                                                              │
                                                                              ▼
                                                                     [언더라이팅 엔진]
                                                                     (요율표 × 팩터 × 크레더빌리티)
                                                                              │
                                                     ┌────────────────────────┼─────────────────────┐
                                                     ▼                        ▼                      ▼
                                             [보험료 산출 스냅샷]      [정책 원장(PocketBase)]   [OpenHash 앵커링]
                                             (재현 가능한 산출근거)                                (분쟁 대비 감사증적)

[사고/이벤트 발생]
     │
     ▼
[이벤트 어테스테이션 게이트웨이] ──(K-Traffic/K-Health/K-119 "발생 여부"만)──▶ [청구 전처리 엔진]
     │                                                                          │
     ▼                                                                         ▼
[기존 /biz/ins-claim (지갑서명)] ◀── 사용자 직접 접수(현행 유지) ──▶  [자동/수동 분기 라우터]
     │                                                                          │
     ├─ 저액·저위험(정액 이벤트형) ──▶ 규칙 기반 자동 승인 ──▶ 제휴사 승인 후 GDC 지급
     └─ 고액·비정형·이의있음      ──▶ 사람 담당자 검토(현행 유지) + AI는 "요약·쟁점정리" 보조만
```

**설계상 핵심 결정**:
1. **언더라이팅 엔진은 원본 PDV를 직접 열람하지 않는다** — 반드시 "PDV 접근 게이트웨이"를 거쳐 스코프에 명시된 집계치만 받는다. 이렇게 하면 언더라이팅 엔진 자체가 유출되더라도 원본 PDV(일기·위치·의료기록 원문)는 노출되지 않는다.
2. **청구 자동화는 "발생 여부 어테스테이션"에서 시작한다** — K-Health/K-Traffic/K-119가 "이런 이벤트가 있었다/없었다"만 서명해서 넘겨주고, 구체적 진단명·정황은 청구 전처리 엔진이 몰라도 되는 상품(§3.2의 정액 이벤트형)부터 자동화한다.
3. **AI(DeepSeek/Claude)의 역할을 "심사 결정권자"에서 "보조자"로 낮춘다** — 청구 서류 요약, 쟁점 정리, 유사 과거 사례 검색까지는 AI가 하되, 최종 지급 여부는 규칙 엔진(저액·저위험) 또는 사람(그 외)이 결정한다. 이건 v1.0 설계에서 가장 크게 후퇴시켜야 하는 부분이다.

## 6. 단계적 로드맵 (제주 필드테스트 기준)

| 단계 | 범위 | 왜 이 순서인가 |
|---|---|---|
| **0단계** | 사물 보험(자동차 UBI) 요율 설계 + K-Traffic 데이터로 리스크 팩터 산출 파이프라인 구축. **실제 보험 계약·지급은 하지 않고, "만약 보험이라면 이런 보험료가 나온다"를 사용자에게 참고 정보로만 보여주는 시뮬레이터 단계** | 법적 인허가 없이도 시작 가능. 요율 모델을 실데이터로 검증하는 게 우선 |
| **1단계** | 트랙 A(MGA) 제휴 보험사 확보 후, 이벤트 기반 정액 소액보험(탑승·배달) 정식 출시 — 지금 있는 `/biz/ins-claim` 담당자 검토 흐름을 그대로 정식 상품에 연결 | 이미 코드가 존재하고, 민감정보 노출이 가장 적은 상품군 |
| **2단계** | 저액·저위험 청구군에 한해 규칙 기반(사람이 미리 정한 조건문) 자동 승인 도입 — "AI가 즉시 심사"가 아니라 "조건을 만족하면 자동 승인, 아니면 사람"으로 명확히 구분해 표시 | 자동화 신뢰도를 실측하며 점진 확대 |
| **3단계** | 정기검진 연동 건강보험 할인 상품(§3.2) — "완료 여부"만 확인하는 수준에서 시작 | 여전히 진단정보 비열람 원칙 유지 |
| **4단계(장기)** | 실손·생명보험 등 정밀 언더라이팅 상품 — 반드시 제휴 보험사의 정식 인수심사 체계에 편입, §4.3 가족력 게이트 재검토는 별도 트랙 | 별도 법률·의료윤리 자문 선행 필수 |
